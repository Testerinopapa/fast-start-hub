# Explee Pipeline QA — GitHub Actions

**Workflow:** [Explee Pipeline QA](../.github/workflows/explee-pipeline-qa.yml)

This lets us run tests, inspect outputs, fix bugs and rerun from GitHub without access to the Explee Supabase projects.

## Automatic offline checks (no secrets, no credits)

Every relevant push and pull request runs:

1. Calendly/HubSpot campaign regression tests (research filtering, classification, evidence and campaign preservation).
2. Context.dev transport mocks and core research tests.
3. Mocked Edge Function endpoint and discovery tests.
4. Deno type checks.
5. A **real executable** local rules-engine report from synthetic saved-company research fixtures.

The fifth step saves **`pipeline-fixtures.json`** and **`pipeline-fixtures.md`**. Each contains the actual campaigns generated by the current source, their audiences, search terms, citation URLs and evaluation checks. The workflow saves separate JUnit XML and text logs for the other suites. Each job uploads an artifact even if tests fail. Failures are **not hidden**: a failed suite causes the overall job to be red.

**This is not a production test.** Fixture tests cannot prove that Context.dev returns relevant live results, that the Supabase backend is deployed, or that contacts actually work.

## How to run and inspect

1. Open **Actions → Explee Pipeline QA → Run workflow** (the workflow must be on the default branch for manual execution).
2. Leave **Live Context.dev** off for the entirely offline run. Optionally choose 3 or 5 repeat runs to look for flaky tests.
3. Open the workflow run and read the **Summary**.
4. Under **Artifacts**, download `explee-offline-qa-...`. Review:
   - `pipeline-fixtures.md` / `pipeline-fixtures.json` — generated campaign output, not canned results.
   - `campaign-tests.xml` / `campaign-tests.log` — relevant audience assertions.
   - `research-tests.xml` / `research-tests.log` — research and provider mocks.
   - `endpoint-tests.xml` / `endpoint-tests.log` — mocked API and discovery flow.
   - `type-check.log` — TypeScript diagnostic output.
5. Share the GitHub Actions run URL here. I can inspect the job, identify failures, change the code and trigger another run via a new push or permitted rerun action.

The repository has previously had type-check and campaign CRUD test failures. This workflow intentionally surfaces them instead of marking the run successful; they must be fixed or separately triaged before using CI as a deployment gate.

## Optional paid live test WITHOUT Supabase

To test fresh company outputs:

1. Add a repository Actions secret named **`CONTEXT_DEV_API_KEY`** under **Settings → Secrets and variables → Actions**. Use a Context.dev key with permissions for web search, URL mapping and scraping. Do not put it in a GitHub variable, issue, commit or chat.
2. Open **Actions → Explee Pipeline QA → Run workflow**.
3. Tick **live_context_dev** and enter a public company URL (e.g. `https://calendly.com`).
4. Run it. The live job writes `pipeline-live.json` and `pipeline-live.md`, available in its Summary/Artifacts.

The live smoke reuses the Phase 4 company search ranking and website verification functions. The prequalification filter skips guides and directories before spending the extra page request. It does not run the full Phase 5 contact extraction, which still requires verified employment evidence.\n\nThe live smoke does:
- URL mapping and **up to 2** structured company scrapes → extract first-party company facts.
- Local zero-credit campaign generation based on those facts.
- Up to **3** search requests for competitor, potential buyer and person **previews**, with **up to 1 extra buyer-company scrape** for evidence-based qualification. Person search is skipped unless the buyer's website identity and potential fit are supported.

Search results are labeled **unverified**. This is not the full persistence-dependent discovery, qualification, or emailing pipeline. No emails are sent and no database writes occur. It does **not** access Supabase.

**Cost warning:** The maximum is 1 URL mapping request, 3 structured scraping requests and 3 search requests. That is a *request cap*, not a guaranteed credit or dollar cap; structured extraction can consume more than one provider credit per request. Live mode runs only on explicit manual opt-in, never on pushes.

## Iteration loop

1. Run offline test, or opt-in to live research after configuring the secret.
2. Inspect JSON + Markdown output and JUnit failures.
3. Make a targeted change to the pipeline or tests.
4. Push a new commit; automatic QA runs again on matching paths.
5. Compare with the previous output before claiming an improvement.

**Don't treat a successful smoke test as verified prospects.** Confirm business identity, audience fit, contact identity and sourcing independently before any outreach.

## Running locally

```powershell
# From repository root, with Deno installed
deno run --allow-env=GITHUB_SHA --allow-write=artifacts scripts/explee-pipeline-fixtures.ts

cd supabase/functions
deno test --allow-env _shared/calendly-regression_test.ts _shared/research-core_test.ts _shared/context-dev_test.ts
deno test --no-check --allow-env _shared/endpoints_test.ts
deno task check
```

Local live smoke (only with a real Context.dev key and explicit approval):

```powershell
$env:CONTEXT_DEV_API_KEY = "<set locally, do not commit>"
$env:EXPLEE_APPROVE_PAID_RUN = "yes"
deno run --allow-env=CONTEXT_DEV_API_KEY,EXPLEE_APPROVE_PAID_RUN,GITHUB_SHA --allow-net=api.context.dev --allow-write=artifacts scripts/explee-pipeline-live.ts https://calendly.com
```

Run the last command from the repository root, not from `supabase/functions`.
