# Explee → OpenOutFind integration

An **optional lead-finding QA stage** using [OpenOutFind](https://github.com/eracle/OpenOutFind) with the campaign data already generated by Explee. Qualification inference routes through an authenticated **Lovable AI** Edge Function rather than a separate OpenAI account. **Does not change Explee's live UI or Supabase backend.** Runs through GitHub Actions so we can compare outputs with Context.dev.

## Current status

- Offline adapter tests run on every relevant push / PR: no credentials, API requests or LLM cost.
- Live qualification is only initiated through **Actions → Explee OpenOutFind Lead QA → Run workflow**, with **run_live** checked.
- Input must be a previous **Explee Pipeline QA** run whose live artifact contains a pipeline-live.json file. Run **44815551658** is an example Calendly research run from November 20, 2026. GitHub artifacts expire; use a new live run after expiration.
- Campaigns are numbered 0–5. Choose the index, request 1, 3 or 5 leads, and leave **upload_leads** off unless you accept the exposure consequences.

These are **provider profile matches and an LLM-generated qualification hypothesis**, not verified employees or customers. Every returned lead is marked "not_independently_verified" for employment and "llm_assessed_not_verified" for customer fit.

## Required GitHub repository secrets

**Settings → Secrets and variables → Actions → Repository secrets**:

| Secret | Used for |
|---|---|
| OPENOUTFIND_LLM_API_KEY | Shared proxy token: must match server-side `OPENOUTFIND_PROXY_TOKEN` in Lovable Cloud; **not an OpenAI API key** |
| OPENOUTFIND_BETTERCONTACT_API_KEY | BetterContact Lead Finder discovery (no work-email purchase in our workflow) |

Optional Actions **repository variable** `OPENOUTFIND_LLM_API_BASE` for the deployed Lovable AI proxy URL. The default currently points to `https://emlggkmtbosahpzrxaul.supabase.co/functions/v1/openoutfind-ai/v1`; override it if Lovable hosts the function elsewhere. The model is fixed to `openai_compatible:openai/gpt-6-luna` to match the proxy schema; the older `OPENOUTFIND_AI_MODEL` variable is ignored. The existing `CONTEXT_DEV_API_KEY` is for research. **Do not add keys to code, issues, logs or artifacts.**

**Expenses:** BetterContact index searches are described as free by upstream; Lovable AI inference consumes Lovable credits. We call **find N --json** and never use **emails** or **--emails**, so no paid email lookup is authorized. The 1/3/5-lead limit is **not a strict token budget**. The additional local `qa_max_ai_calls` limit (8, 12 or 16, default 12) stops outgoing LLM HTTP calls **before** the cap is exceeded. It limits request count, not total credits/tokens per request. The server-side 40-call/run and 100-call/day safeguards remain in force; GitHub's 30-minute timeout provides an additional ceiling.

## Lovable AI deployment requirements

The `openoutfind-ai` Edge Function code and the migration under
`drizzle/migrations/0000_openoutfind_ai_safeguards.sql` must be applied to the
**actual Lovable/Supabase backend hosting the function**, not merely committed
to GitHub. Version-controlled `supabase/config.toml` sets
`[functions.openoutfind-ai] verify_jwt = false`; the endpoint enforces an
independent **application Bearer token**, rather than a Supabase user JWT.

Set `OPENOUTFIND_PROXY_TOKEN` as an Edge Function secret in that backend.
The same randomly generated token must be stored in GitHub repository secret
`OPENOUTFIND_LLM_API_KEY`. Do not use the managed `LOVABLE_API_KEY` as that
token or put it in a GitHub Variable.

**Read-only preflight:** authenticated `GET /models` verifies the token and
advertised model without invoking inference or reserving SQL quota. It does
**not** prove that SQL migrations ran or that tool-call completions work;
those require a separate explicitly requested credit-consuming live test.

HTTP 404 means wrong endpoint or function not deployed. HTTP 401 means token
mismatch or the platform JWT gate is enabled. HTTP 503 means missing backend
configuration. BetterContact credentials are checked in a separate live run.

## Privacy

Pinned OpenOutFind upstream SHA: **352efd65a84e9106cd08504d2714cd7f5b7bce44** (November 16, 2026), Apache-2.0.

OpenOutFind's upstream **central contacts store** may pool professional profiles, company records and work emails at hub.openoutreach.app. In this pinned source, its client needs an operator email or store API token to register. The Actions job clears both:

- OPENOUTFIND_OPERATOR_EMAIL is empty
- OPENOUTFIND_CONTACTS_API_TOKEN is empty

With neither, the upstream's shared-store client has no token and does not send contacts to the maintainer's hub. **Do not add either variable** to this workflow without a privacy review. Requests still go to BetterContact and the LLM provider. For an additional hard network guarantee, run in an egress-restricted private runner.

Explee's repository is public. **Detailed personal lead reports are not uploaded by default** and do not appear in job logs or summaries. Only aggregate counts are uploaded. Enabling **upload_leads** deliberately uploads personal names and professional URLs to a one-day GitHub Actions artifact; avoid that for sensitive data. Detailed results are ephemeral otherwise.

## How it connects

The adapter reads the previously produced Explee research JSON, then:

1. Prepares a researched product brief, campaign target hypothesis and explicit conservative lead-fit rules from the selected campaign. The rules are passed with OpenOutFind's `--brief` rather than consuming an AI request to generate a brief.
2. Invokes pinned OpenOutFind against BetterContact, routing inference through the non-retrying Lovable AI proxy using `scripts/run_openoutfind.py`, with a temporary database and no email lookups.
3. Normalizes its JSONL results to a structured Explee-compatible JSON file with lead names, companies, titles, professional profile URLs, and qualification reasons.
4. Marks every person's employment and buyer fit as **not independently verified**.
5. Writes per-stage AI request counts and a typed QA outcome (`goal_met`, `partial` or `no_leads`) to `openoutfind-qa.json`. The HTTP gate rejects further requests locally when `qa_max_ai_calls` is reached, without spending the backend's remaining allowance. 
6. Uploads only aggregate summaries by default, including **partial results even if the provider exits nonzero**. The GitHub job still **fails** whenever it misses the requested count, so a partial result cannot masquerade as a successful run.

No emails are purchased or sent; no results are written into Supabase. This currently supports our **GitHub QA pipeline**, not an in-app OpenOutFind button.

## How to run

1. Run **Explee Pipeline QA** with live_context_dev enabled to create a recent pipeline-live.json artifact.
2. Open **Explee OpenOutFind Lead QA**, click **Run workflow**, select run_live, supply the earlier source_run_id, select campaign_index, lead_count and `qa_max_ai_calls` (8, 12 or 16). The cap is enforced per job attempt, not an unlimited retry allowance.
3. Inspect the job Summary and `explee-openoutfind-summary-<runid>` artifact, which now contains `openoutfind-summary.json` and `openoutfind-qa.json` with only aggregate metrics. Inspect the `ai_requests_by_phase` counters to see whether time and credits were spent on initial searches, guesses or individual judgments. To inspect individual records, use private storage or the explicitly opt-in personal artifact and validate them against first-party company/team pages before outreach; **a public repository's Actions artifact is not private storage**.
4. Share the GitHub Actions run link so we can assess results, fix problems, and repeat.
